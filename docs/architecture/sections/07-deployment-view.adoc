[[deployment-view]]
== Verteilungssicht

=== Beobachteter Stand

* Storybook wird lokal mit `npm run storybook` betrieben.
* `npm run build-storybook` erzeugt die statische Veröffentlichung.
* `.github/workflows/deploy-webspace.yml` baut das Storybook und überträgt es per rsync über SSH auf den All-Inkl-Webspace (ui.hoopsfoundry.com); `deploy/htaccess` liefert HTTPS-Umleitung und Sicherheits-Header. `.github/workflows/deploy-storybook.yaml` (GitHub Pages) ist nur noch der manuelle Rückfall.
* `.github/workflows/publish-npm.yml` veröffentlicht beim Push eines Tags `v*` per Trusted Publishing (OIDC) auf npm.
* React-Artefakte werden über `npm run build:react` erzeugt.
* `package.json` definiert die Inhalte und öffentlichen Exports des Pakets.

Der gelesene Deployment-Workflow führt Tests und Typprüfung nicht explizit aus. Ein Qualitätsworkflow ist eine geplante Ergänzung, kein vorhandener Nachweis.

=== Webspace und npm

* Webspace: Gebaut wird auf GitHub (kein Node auf dem Webspace). Zugangsdaten sind Repository-Secrets (`DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`, `DEPLOY_PATH`); der Schlüssel gehört einem eingeschränkten Benutzer, der Host-Schlüssel wird geprüft (`StrictHostKeyChecking=yes`). Der Workflow läuft bei jedem Push auf `main`; manuell startet er mit `dry_run: true` (Standard) und zeigt mit `rsync -n` nur die Änderungen. Probelauf und erster echter Lauf sind auf GitHub durchgelaufen. `--delete` entfernt Altdateien, der Ordner `releases/` bleibt. Die Tests prüfen Aufbau und Regeln (`tests/deploy-workflows.test.ts`).
* npm: `publish-npm.yml` läuft beim Push eines Tags `v*` (zum Wiederholen manuell mit dem Tag als Ref), mit `id-token: write` und ohne Token. Voraussetzung ist ein Trusted Publisher bei npm mit genau diesem Dateinamen. Der Tag muss `v<version>` aus `package.json` heißen, sonst bricht der Lauf ab. Das Secret `NPM_ATOKEN` wird nicht verwendet. Der Aufbau folgt dem Release-Workflow von Open Coaching Format.

=== Vanilla-Auslieferung

Entscheidung und Begründung: ADR-006.

Bis Version 1.0 ist das GitHub-Release mit `dist/vanilla` der Weg, ab 1.0 npm; der Aufbau von `dist/vanilla` bleibt. `dist/vanilla` enthält drei Bündel nebeneinander: `hoops.js` (Kern), `hoops-render.js` (importiert `./hoops.js`) und `hoops-map.js` (Karte, steht allein, siehe ADR-007); die Dateien einer Version gehören zusammen kopiert, die Karte dazu Leaflet aus dem Projekt (`leaflet.css`, `leaflet-src.esm.js`).

[cols="1,2,2",options="header"]
|===
|Schritt |Wo |Was
|Bau und Release-Dateien |Entwicklungsrechner oder Workflow `release-vanilla.yml` |`npm run build`, dann `node scripts/release-vanilla.mjs`: prüft die Version an acht Stellen und die Größenbudgets, schreibt `release/hoops-ui-<version>.tgz`, `.sha256`, `.tgz.sha256`, `manifest.json`, `hoops-sync.mjs` und `hoops-sync.mjs.sha256`
|Veröffentlichung |GitHub-Release `v<version>` |Die sechs Anhänge; angelegt vom Release-Job des Workflows bei einem Tag `v*` (Tag-Commit auf `main`)
|Übernahme |Projekt des Portals, `hoops-sync.mjs --from-release <version>` (npm: `npx hoops-sync --from-package`) |Download über https, Prüfung, Ersetzen von `_site/hoops` mit Rückrollen und Sperre; Leaflet aus `node_modules` nach `_site/vendor/leaflet`
|Betrieb |Statischer Host (GitHub Pages) |Dateien auf der eigenen Domain, relative Pfade (auch unter `/<repo>/`); strenge CSP (`script-src 'self'` plus Hash des Boot-Skripts, `style-src 'self'`, `img-src 'self'` und Kachel-Host)
|===

Nachgewiesen ist der Weg durch `scripts/check-portal-seite.mjs`: bauen, Release erzeugen, den Anhang `hoops-sync.mjs` in einem fremden Ordner mit `--from-release` von einem lokalen Server laufen lassen und die Beispielseite unter strenger CSP in Chromium und WebKit prüfen (auch unter einem Unterpfad, bei 320 px und ohne JavaScript). Das Hilfsskript und das Release-Skript sind mit Node 18.20.8, 20.20.2 und 22.21.0 gelaufen. Nicht nachgewiesen ist der Lauf des Workflows `release-vanilla.yml` auf GitHub (kein Tag, kein Release erzeugt); ein Test prüft nur seinen Aufbau und führt die Versionsprüfung in bash aus (Auslöser, Rechte, Reihenfolge, Pins). Er lässt sich mit `workflow_dispatch` und `dry_run: true` ohne Release erproben. Die Prüfsummen sind keine Signatur; Build-Provenance ist vorbereitet, aber nicht eingeschaltet.

=== Dokumentation und MCP

Der Workflow `.github/workflows/render-docs.yml` (Vorlage: Workflow „Render AsciiDoc Documentation" im Vereinsregister) löst bei Änderungen an `docs/**/*.adoc` auf `main` mit `asciidoctor-reducer` alle Includes von `docs/architecture/index.adoc` auf und committet das Ergebnis als `docs/architecture/README.adoc`. Damit zeigt GitHub das Gesamtdokument an. Mermaid-Diagramme erscheinen dort als Quelltextblöcke; ein grafisches Rendering (z. B. asciidoctor-diagram) ist nicht Teil dieses Schritts. Eine statische Storybook-Veröffentlichung ist nicht automatisch ein laufender MCP-Dienst. Lokale und öffentlich gehostete MCP-Nutzung benötigen getrennte Betriebsentscheidungen.
