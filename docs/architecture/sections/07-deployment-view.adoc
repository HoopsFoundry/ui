[[deployment-view]]
== Verteilungssicht

=== Beobachteter Stand

* Storybook wird lokal mit `npm run storybook` betrieben.
* `npm run build-storybook` erzeugt die statische Veröffentlichung.
* `.github/workflows/deploy-storybook.yaml` baut und veröffentlicht auf GitHub Pages.
* React-Artefakte werden über `npm run build:react` erzeugt.
* `package.json` definiert die Inhalte und öffentlichen Exports des Pakets.

Der gelesene Deployment-Workflow führt Tests und Typprüfung nicht explizit aus. Ein Qualitätsworkflow ist eine geplante Ergänzung, kein vorhandener Nachweis.

=== Vanilla-Auslieferung

Entscheidung und Begründung: ADR-006.

Bis Version 1.0 ist das GitHub-Release mit `dist/vanilla` der Weg, ab 1.0 npm; der Aufbau von `dist/vanilla` bleibt. `dist/vanilla` enthält drei Bündel nebeneinander: `dss.js` (Kern), `dss-render.js` (importiert `./dss.js`) und `dss-map.js` (Karte, steht allein, siehe ADR-007); die Dateien einer Version gehören zusammen kopiert, die Karte dazu Leaflet aus dem Projekt (`leaflet.css`, `leaflet-src.esm.js`).

[cols="1,2,2",options="header"]
|===
|Schritt |Wo |Was
|Bau und Release-Dateien |Entwicklungsrechner oder Workflow `release-vanilla.yml` |`npm run build`, dann `node scripts/release-vanilla.mjs`: prüft die Version an acht Stellen, schreibt `release/dss-vanilla-<version>.tgz`, `.sha256` und `manifest.json`
|Veröffentlichung |GitHub-Release `v<version>` |Anhänge: Tarball, Prüfsummen, Manifest; angelegt vom Release-Job des Workflows bei einem Tag `v*`
|Übernahme |Projekt des Portals, `portal-sync.mjs --from-release <version>` |Download, Prüfung, Ersetzen von `_site/dss`; Leaflet aus `node_modules` nach `_site/vendor/leaflet`
|Betrieb |Statischer Host (GitHub Pages) |Dateien auf der eigenen Domain; strenge CSP (`script-src 'self'` plus Hash des Boot-Skripts, `style-src 'self'`, `img-src 'self'` und Kachel-Host)
|===

Nachgewiesen ist der Weg durch `scripts/check-portal-seite.mjs`: bauen, Release erzeugen, mit `portal-sync --from-release` von einem lokalen Server holen und die Beispielseite unter strenger CSP in Chromium und WebKit prüfen. Nicht nachgewiesen ist der Lauf des Workflows `release-vanilla.yml` auf GitHub (kein Tag, kein Release erzeugt); ein Test prüft nur seinen Aufbau (Auslöser, Rechte, Reihenfolge). Er lässt sich mit `workflow_dispatch` und `dry_run: true` ohne Release erproben.

=== Dokumentation und MCP

Der Workflow `.github/workflows/render-docs.yml` (Vorlage: Workflow „Render AsciiDoc Documentation" im Vereinsregister) löst bei Änderungen an `docs/**/*.adoc` auf `main` mit `asciidoctor-reducer` alle Includes von `docs/architecture/index.adoc` auf und committet das Ergebnis als `docs/architecture/README.adoc`. Damit zeigt GitHub das Gesamtdokument an. Mermaid-Diagramme erscheinen dort als Quelltextblöcke; ein grafisches Rendering (z. B. asciidoctor-diagram) ist nicht Teil dieses Schritts. Eine statische Storybook-Veröffentlichung ist nicht automatisch ein laufender MCP-Dienst. Lokale und öffentlich gehostete MCP-Nutzung benötigen getrennte Betriebsentscheidungen.
